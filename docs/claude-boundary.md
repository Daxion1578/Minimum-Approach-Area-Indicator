# Claude に任せること・任せないこと

MAAI は安全に関わる道具なので、どこを人と決定論コードが持ち、どこを Claude に任せるかを先に決めている。使い方を増やしたら1行足す。「なぜそれか」が書けない行は、使う理由が無いということなので消す。

## 任せない（決定論コードと人が持つ）

| こと | 持つ場所 | 理由 |
|---|---|---|
| 課電判定（どの導体が生きているか） | `engine/energize.py` | 系統の接続と開閉器の状態から一意に決まる。推論の余地を残すと事故になる |
| 距離・干渉・包絡の計算 | `engine/` | 幾何は計算で出る。LLM に数値を決めさせない |
| 作業日の停止範囲（どこを切るか） | `engine/steps.py` | 流入端すべてで最初の断路器まで切る、という決まりで一意に決まる。切り忘れは充電部への接近になる |
| 重機の選定（一番小さいクラスと据付位置） | `engine/crane_select.py` | 荷重表・作業半径・離隔の計算で決まる。クレーンの大きさは費用にも安全にも直結するので、推論させない |
| 提案の採否 | 人 | 現場の責任は人にある。Claude の提案は必ずエンジンで再検証してから表示する |
| 外に出す情報の選別 | `agent/mask.py`（置換表） | 社内情報を外部に出せない現場で使える前提条件。線路名・所名・地名に加えて、定格値（容量・遮断電流など）と手元の禁止語リストの語も符号に置き換え、戻すのはローカル。決定論で動き、モデルを呼ばない |
| 図面からの結線の読み取り（どの導体が何につながるか） | `ingest/pdf_sld.py` | 線の太さ・交点・記号の位置で決まる。Claude に接続を決めさせると、間違いが静かに通る |
| 図面からの位置・高さの読み取り | `ingest/pdf_layout.py`、`synth/drawing_rules.py` | 図面の流儀を規則にして生成側と読む側で共有し、決定論で逆変換する。読めない文字・合わない番号は要確認として人に戻す |
| 修正案の候補づくりと再判定 | `engine/propose.py` | 候補はパラメータの組み合わせで列挙でき、各候補は同じ判定器にかけるだけ |

## 任せる（Claude が持つ）

| こと | 場所 | なぜ Claude か |
|---|---|---|
| 工事の依頼文の読み取り：取り替える機器・止められない設備・資材置場・重さ | `agent/intake.py`（確かめは `engine/intake.py`） | 「1 号バンク」「遮断器の西 8 m」のような現場の言い方を、構内の機器と座標に結びつけるのは規則では書き切れない。番号の実在と矛盾は計算で確かめ、人が入れる。止められない設備は追加停止の候補から外れ、計算の答えが変わる |
| 取り込んだ図面の意味づけ：開閉器の種別の確認、名前の無い導体の説明、人に確かめてほしい点の文章 | `agent/structure.py` | 図面の読み方（番号の形・つながりから何かを判断する）は「人の読み方」の再現で、LLM が一番効く。規則と食い違う種別は上書きせず質問にして人に戻す |
| 修正案の説明：候補ごとに何を変え、何が良くなり、何を犠牲にするか。順位づけの理由 | `agent/explain.py` | 候補と判定値はエンジン。現場の人に伝わる文章と、停止調整の要否のような含みの説明は判断の言葉の仕事 |
| 呼べないときの代替 | `agent/structure.py` `agent/explain.py` の規則 | キー無し・オフラインでも全画面が動く。Claude が無くても安全判定は変わらない、という設計の証明にもなる |

この先（まだ作っていない）: 作業指示の自然文から制約（止められない回線、作業対象、重機）を取り出す。停止要否検討書の文章。

## 開発でどう使ったか（Claude Code）

| 仕組み | 何のため | なぜその仕組みか |
|---|---|---|
| `CLAUDE.md` | 変わらない約束（公開制約、安全設計の原則、報告の型） | 毎回のセッションで必ず読まれる唯一の場所 |
| Skill `/daily` `/wrap` | 朝と夜の決まった手順 | 本人が覚える操作を2つに絞る |
| Skill `/slice` `/verify` `/report` | 縦切りの計画、手元確認の手順、`STATUS.md` の更新 | 手順を人が毎回言い直すと抜ける。型として固定する |
| Skill `/critique` | 外の目で点検し、足りないものを残す | 自分の作品は自分では客観視できない。批評をコミットすれば試行錯誤の記録になる |
| Skill `/publish-check` | 公開前点検 | 社内情報の混入は取り返しがつかない。人の記憶に頼らない |
| サブエージェント `safety-reviewer` | push・提出前の点検係（読み取り専用） | 書いた本人と同じ文脈では見落とす。別の文脈で独立に読ませる |
| サブエージェント `task-keeper` | `TASKS.md` の保守（残り・順序・落とす順） | 作業中の文脈に混ぜると、予定が実況に流される。別の係に持たせる |
| フック `pre_git_safety` | commit/push 前に禁止語・秘密情報・緯度経度・実図面形式を検出 | 人が忘れる作業は機械に。`--no-verify` も拒否 |
| フック `post_edit_tests` | `engine/` `contracts/` `tests/` 編集後に pytest を自動実行 | テストが落ちた状態で先に進ませない |
| モデルの使い分け | 意味づけと説明で別のモデルを指定できる（`.env` の `MAAI_MODEL_STRUCTURE` / `MAAI_MODEL_PROPOSE`） | 遅延・精度・コストが用途で違う。今はどちらも同じ既定値 |
| MCP サーバ（今週は未採用） | `agent/tools.py` を MCP として公開し、開発中の Claude Code と製品の提案ループが同じ道具を使う案 | 道具を一つにすると、開発中に見つけた不具合がそのまま製品の修正になる。動くものができてから判断する（`docs/spec.md` §13） |
