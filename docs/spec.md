## 1. 一文と本質

人が減る現場で、止めきれない充電部との距離を、人の目だけに頼らない形にする。

本質（※仮）: 停止の段階ごとに変わる「近づけない領域」を、図面と停止手順から計算し、工事で動くすべてのもの（クレーン、吊り荷、搬入車両、仮置き資材、撤去品）に対して「その段階で、その空間は使えるか」に答える基盤。

- 3層で考える。下: 変わらない前提（図面・充電部の位置・電圧ごとの離隔）。中: 段階ごとに変わる近づけない領域（MAAI の核、`envelope.json`）。上: 工事で動くものについての問い（施工計画のたびに変わる）。
- 工程表（日付・人員・段取り）と配置図の作図は扱わない。停止の順番（第1段・第2段…）と、動くものの占める空間だけを受け取る。
- 価値が積み上がるのは中の層。一度作れば、次の問い・次の工事会社・AR・機械に同じ形で使い回せる。

## 2. 解く課題（Known）

- 変電所の更新工事は、運転中の構内で設備の一部を入れ替える。作業箇所の周りは停止するが、受電回線や母線は片側しか止められず、隣に充電部が残る。そこへクレーンが入ると、作業半径が充電部に近づく場所ができる。
- その危険は図面に描かれていない。系統の接続と開閉器の状態から計算して初めて分かり、停止ステップごとに変わる。空間に線は引けない。
- 今は担当者が、単線結線図を頭の中で課電・停止に塗り分け、配置図と作業半径を目で合わせ、停止申請の文面と突き合わせて決めている。人が減り経験者が替わると、この判断が再現できなくなる。
- 現場では専任監視者の目視に頼っており、目を離した一瞬が重大災害につながる。
- 設備は長く使われる（遮断器で40年前後、変圧器で60年近くが目安）。一つの変電所は数十年に何度も更新を受け、そのたびに図面と停止条件が変わる。道具とデータはそれより長く読める必要がある。

## 3. 使う人と場面（11/3 確定）

- 使う人: 電力会社の工事担当。自分で停止計画（どの開閉器を開け、どこに接地するか）を組み、工事会社の施工計画（クレーンの機種・据付位置）を確認する人。
- 場面: 工事の内容が決まった段階で、停止状態を道具の中で組み、その結果どの導体が充電のまま残るかを見て、クレーンが近づきすぎないかを確かめ、可・条件付き可・不可と根拠の図を出す。足りなければ追加停止か配置変更の案を受け取り、採否を決める。系統側の最終判断（停止の可否）は人が持つ。
- 入力: 手元の CAD から出した図面（ベクター PDF または DXF。結線図・配置図・断面図）、工事内容、施工計画。
- 今との差: 頭の中の塗り分けと目視の重ね合わせが、誰がやっても同じ結果になり、根拠が残る。保守的に取っていた予防停止を減らせる。
- 将来: 承認済みの包絡を現地の監視者（AR）と機械（クレーン側の装置）に届ける。今週は書き出しまで。
- 退けた案: 停止範囲を決まったものとして受け取るだけの側（実務の頭の使い方とずれる）、工事会社の施工計画担当（電力会社の図面を渡す前提が要る）。

## 6. データ契約（Known。`contracts/*.schema.json` に落とす）

共通メタ: `schema_version`（例 "0.1"）、`site_id`（符号。例 "SITE-01"）、`source_drawing_hash`（元DXFのsha256）、`generated_by`。

### 6.1 topology.json — 図面の構造（開閉器の状態は含めない）
```json
{
  "schema_version": "0.1",
  "site_id": "SITE-01",
  "source_drawing_hash": "sha256:...",
  "nodes": [
    {"id": "LINE-A",  "kind": "source",      "voltage_kv": 66},
    {"id": "DS-A1",   "kind": "disconnector","voltage_kv": 66},
    {"id": "CB-A",    "kind": "breaker",     "voltage_kv": 66},
    {"id": "BUS-1",   "kind": "bus",         "voltage_kv": 66},
    {"id": "ES-B2",   "kind": "earthing",    "voltage_kv": 66, "attached_to": "DS-B2"},
    {"id": "TR-1",    "kind": "transformer", "windings": {"hv": {"voltage_kv": 66}, "lv": {"voltage_kv": 6.6}}}
  ],
  "edges": [
    {"from": "LINE-A", "to": "DS-A1", "conductor": "bare"},
    {"from": "DS-A1",  "to": "CB-A",  "conductor": "bare"},
    {"from": "CB-A",   "to": "BUS-1", "conductor": "bare"}
  ],
  "questions": [
    {"at": "DS-B1", "issue": "label_ambiguous", "options": ["DS-B1", "DS-B2"], "evidence": "TEXT@(120.0,45.0)"}
  ]
}
```
- `kind`: source | bus | breaker | disconnector | earthing | transformer | terminal | load
- 変圧器は内部的に `TR-1.hv` / `TR-1.lv` の2端子に展開し、巻線をまたぐ辺で結ぶ（課電は両方向に伝わる）。
- `earthing` は端点が一つの特殊ノード。`attached_to` の側に接地する。
- `questions` は構造化時にClaudeが出す未確定箇所。承認時に空であること。

## 7. エンジン（決定論。Known）

### 7.1 課電判定 `engine/energize.py`
- 閉じた開閉器と導体でつながる連結成分を求める。成分に `live` な電源が含まれれば `live`。含まれず、閉じた接地開閉器があれば `dead_grounded`、無ければ `dead_ungrounded`。`live` かつ接地あり → `invalid` としてエラー。
- 変圧器は巻線をまたいで伝播（両方向）。電圧階級はノード固有で、伝播で変わらない。
- 保守的既定: `treat_ungrounded_as_live = true`（未接地の停止区間は包絡計算では課電扱い）。設定で切替可。

### 7.2 幾何 `engine/geometry.py`
- すべてカプセル。線分と線分の最短距離（3D）を1関数で持ち、カプセル同士は `dist < r1 + r2` で干渉。
- テスト: 平行・交差・ねじれ・端点同士・退化（点）の5ケース。

### 7.3 安全包絡 `engine/envelope.py`
- `live`（設定により `dead_ungrounded` も）な導体プリミティブごとに、半径 = 導体半径 + 離隔距離。
- 離隔表 `data/tables/clearance.csv`: 電圧階級 → 離隔（m）、出典列つき。既定値は公開通達の目安（低圧 1.0m、高圧 1.2m、特別高圧 2.0m、60kV以上は10kVごとに0.2m加算）。会社基準は設定で上書きする欄を空けておく。原文照合は §16。
- 法的な枠組みの記述（READMEと画面の注記用）: 労働安全衛生規則 第349条（充電電路に近接する場所でのクレーン等の作業）。

### 7.4 重機 `engine/machine.py`
- ベース位置、旋回中心高さ、ブーム長、起伏角、旋回角の範囲。旋回角を2°刻みでサンプルし、各姿勢でブーム（カプセル）と、先端から下がるフック・吊荷（鉛直カプセル）を生成。
- 諸元 `data/tables/cranes.csv` は公開カタログ水準の例示値。「例示値」と明記。

### 7.5 干渉判定 `engine/interference.py`
- 全姿勢 × 全包絡の最短距離を計算し、`distance < clearance` を違反として列挙。最小距離と違反姿勢を返す。
- 出力はそのまま `interference.json`。

### 7.6 ステップ `engine/steps.py`
- `plan.steps` を順に `state` に適用し、各ステップで課電判定と包絡を再計算。`work_allowed` のステップで干渉が無いことが計画の合格条件。
- タイムライン = ステップ配列の結果。UIのスライダーがこれを再生する。

### 7.7 判断ルール `data/rules/rules.json`
- 一般的な運用原則を、id・条件・説明で持つ。例: R1 受電回線は少なくとも1回線を活かす、R2 変圧器は少なくとも1バンク運転継続、R3 母線は片側のみ停止可、R4 作業対象の両側を停止し接地してから作業、R5 接地は停止区間にのみ投入（エンジンが `invalid` で強制）、R6 離隔の余裕が閾値未満なら監視員配置を必須。
- 機械的に判定できるもの（R1, R2, R4, R5）は `engine/rules.py` で判定。Claudeには全ルールの文面を渡す。会社固有の数値は入れない。

### 7.8 書き出し `engine/export.py`
- `envelope.json`（§6.5）と glTF（`trimesh` でカプセルをメッシュ化して `.glb`）。承認済みのものだけ書き出せる。

## 8. Claude 層（Known）

### 8.1 境界
| Claudeに任せる | 任せない |
|---|---|
| DXFの候補グラフ＋文字＋ブロック名から、機器種別・番号・電源・電圧階級を意味づけしてトポロジJSONを作る。迷いは質問に落とす | 課電判定、離隔の値、距離計算、干渉判定、ステップの適用 |
| 作業指示の自然文から制約（止められない回線、作業対象、重機）を抽出 | 承認（人） |
| 干渉時に修正案（追加操作・配置変更・措置）を立案し、日本語で根拠を説明 | 提案の採否（エンジン検証＋人） |

### 8.2 図面構造化 `agent/structure.py`（優先度10）
1. `ingest/dxf_extract.py` が LINE / LWPOLYLINE / INSERT（ブロック名・位置・回転）/ TEXT を抽出し、端点一致（許容誤差は図面単位で設定）で候補グラフを作る。交差のみの線はつながない。
2. 候補グラフ・文字・ブロック名・凡例をClaudeに渡し、`topology.json` と `questions` を返させる。
3. 画面で質問に答えて承認。承認時に `source_drawing_hash` を固定。
- 対象はブロック記号の図面。線で直描きされた記号は対象外（READMEに明記）。

### 8.3 提案ループ `agent/propose.py`（優先度6）
- 入力: 干渉結果、現在の `state` と `plan`、`constraints`、ルール全文、候補配置（2〜3点）。
- 出力: `proposal.json`。エンジンが `ops_added` を適用 → ルール判定 → 課電 → 包絡 → 干渉を再計算し、結果をClaudeに返す。通るまで最大5回。
- 往復はすべて `logs/proposals/<site>/<timestamp>.jsonl` に保存し、画面に表示。
- 守ること: 図面に無い機器idを出さない（スキーマで `enum` 制約）。自由文は `rationale` のみ。

### 8.4 ツール定義 `agent/tools.py`
- `energize(state)`, `build_envelopes(state)`, `check_interference(state, machine)`, `apply_ops(plan, ops)`, `check_rules(state, plan)`。すべて `engine/` の関数の薄い包み。

### 8.5 モデルと動作モード `agent/client.py`
- 構造化は軽いモデル、提案は上位モデルを既定にし、`.env` で差替え。理由（遅延・精度・コスト）をREADMEに一段落。
- `MAAI_OFFLINE=1` またはキー無しで、構造化は `data/sites/<site>/truth/topology.json` を読み、提案はルールベース代替（隣接断路器の追加開放＋接地、候補配置の順送り）。
- Managed Agents / Agent SDK の採用は 11/3 のセッション後に判断（§16）。既定は素のメッセージAPIのツール呼び出しループ。

### 8.6 マスキング関門と監査 `agent/mask.py`, `agent/audit.py`
- 許可リスト（外に出してよい項目）: ノードid（符号）、種別、電圧階級、接続関係、開閉器状態、構内ローカル座標、ステップ、干渉の数値、ルール文面、符号化済みの作業指示文。
- 禁止（出さない）: 実名・事業者名・需要家名・専用線名、住所・緯度経度・地図、容量類（変電所容量・バンク容量・短絡容量・潮流）、需要・契約、整定、警備、暦日の停止時期。
- 作業指示文は辞書＋パターン（固有名詞＋「発電所／太陽光／工場／線／支線」など）で符号化し、対応表 `aliases.local.json` はローカルにだけ置く（合成データのデモ用のみコミット）。
- 送信ごとに `logs/outbound/` に時刻・目的・項目一覧・ペイロードのsha256・モデル名を記録。

## 9. 画面（Known。単一HTMLアプリ、タブ＝導線）

1. 図面取込: DXF選択（またはサンプル）→ 左に元図（DXF→SVG）、右に読み取り結果の重ね表示 → 質問箇所が点滅、クリックで回答 → 承認。
2. 停止条件: 作業指示文の貼付（符号化のプレビューを表示）→ 開閉器状態の設定またはステップ選択 → 3Dで `live`=赤、`dead_grounded`=緑、`dead_ungrounded`=黄、包絡は半透明 → スライダーでステップを再生。
3. 重機配置: 機種選択 → 平面図でベース位置と旋回範囲をドラッグ → 干渉を赤線と数値で表示 → 「修正案を求める」→ 提案と往復ログ → 採用で再判定。
4. 計画確定: ステップ表、反転した系統図、承認ボタン（未確認／承認）→ 承認でハッシュ付与 → 包絡の書き出し（JSON, glb）と印刷用HTML。
5. 現地（条件付き）: `web/ar.html`。WebXR（Android Chrome）で基準点2つをタップして位置合わせ、包絡と機器状態を実寸で重ねる。
   - 位置合わせ検証の試作（11/4 夜、2〜3時間）で確かめること: 床面検出、基準点2点タップでの位置合わせ、高所カプセル（例: 高さ7.5mの母線）の表示、10〜20m歩行時のずれ、メジャー実測との誤差、屋外の明るさでの視認性。結果は数値で `docs/ar-check.md` に残す。
   - 試作の場所は駐車場・公園など。テープで基準点を置き、合成レイアウトをその場の寸法に合わせる。

3Dの機器はカプセルと簡単な柱で十分。見た目より判定の正しさ。

## 10. 合成データ生成器（Known）`synth/gen_site.py`

- 入力: サイト定義JSON（トポロジ＋配置＋状態＋計画）。出力: 結線図DXF 3種、配置図DXF、`truth/topology.json`、`layout.json`、`state_*.json`、`plan.json`、作業指示文、正解の課電・干渉。
- 3種の描き分け: A 整った図（ブロック名が素直、文字は記号の横）、B 名前と配置の揺れ（ブロック名を変える、文字をずらす、端点に0.3mmの隙間、表題欄の雑音文字）、C 母線を分割ポリライン＋回転文字＋別の記号体系。
- サイト: SITE-01 66kV 2回線受電・単母線・2バンク（作業: B回線遮断器の取替。A回線・母線・1バンクは止められない）。SITE-02 最小構成（1回線1バンク、テスト用）。SITE-03 複母線＋母線連絡（構造化の未調整データ）。
- 電圧階級・寸法・クレーン諸元は例示値。実在の設備・社内様式を写さない。

## 11. 評価（Known）`scripts/run_eval.py`

- 図面構造化: 3サイト×3種に対し、ノード種別の一致率、辺のF1、電源・接地の同定率。結果は `data/eval/results.json` と README の表。
- 提案ループ: `rules.json` あり／なしで、ルール違反の提案数と収束までの往復数。
- 評価は最初のコミット群に含める（評価が先、機能が後）。

## 12. 扱う情報（Known）

- 持つのは、機器種別、接続関係、電圧階級、構内ローカル座標、開閉器状態、ステップ順序だけ。
- 回線・引込の識別子は最初から符号。実名との対応表は別ファイル・別権限でローカルのみ。
- 座標は構内ローカル原点。地図・GNSSと結び付けない。
- ファイルは変電所・工事件名ごとに閉じる。横断検索・一元DBは作らない。
- 書き出しは符号と相対ステップのみ。暦日を含めない。
- 承認済み成果物には元図面ハッシュ・承認者（符号）・相対時刻を結び、改ざんを検知できる形にする。
- ハッカソンの全データは合成で、符号化のデモ用に架空名だけを置く。

## 13. 技術構成（Known）

- Python 3.11+（engine, ingest, agent, synth, server）。依存: ezdxf, fastapi, uvicorn, anthropic, numpy, trimesh, pytest, python-dotenv, jsonschema。
- Web: 素のHTML/JS（ESモジュール）、three.js をimportmapでCDN読込。ビルド無し。
- 理由: 保守者1人で読んで直せる範囲に収める。3DはどのみちJS。フレームワークを入れると非開発者が詰まる場所が増える。
- データ設計の原則（設備寿命に合わせる）: 図面が正でJSONは派生物（ハッシュで結ぶ）、開いた形式のみ（DXF入力、JSON/glTF出力、スキーマに版番号）、判断ルールをファイルとして分離、依存を少なく。

## 15. 完成の定義と手元確認（Known）

「動いた」= SITE-01 で、図面取込→停止条件→重機配置→修正提案→承認→書き出しが、ローカルで通しで再現できること。

縦切りごとの確認手順（Claude Code は各縦切りの最後にこの形で手順を提示する）
- 縦切り1: `python -m pytest -q` が通る。`uvicorn server.app:app` を起動し http://localhost:8000 を開く。SITE-01 の状態「通常」で全導体が赤、状態「停止後」でB回線の区間が緑、包絡が半透明で見える。
- 縦切り2: 重機を母線の近くに置くと赤線と最小距離が出る。遠ざけると消える。スライダーでステップ3に進むと包絡が縮む。
- AR 試作: Android Chrome で `web/ar.html` を開き、テープの基準点2つをタップすると合成レイアウトの包絡が表示される。基準点上のカプセル端とテープのずれ、10〜20m歩いた後のずれを測って `docs/ar-check.md` に書く。
- 縦切り3: 干渉状態で「修正案を求める」を押すと、提案と往復ログが出て、採用後に干渉が消える。`python scripts/run_eval.py` が表を出す。
- 縦切り4: 承認すると `data/sites/SITE-01/approved/` に JSON と glb ができる。リプレイで警報が鳴る。
